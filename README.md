# Urbit-native Bitwarden desk — synthetic-data preview

This native Bitwarden Gall desk connects official Bitwarden clients to Connect's reusable local-resource authorization through Enterprise SSO. The backend implements CLI, browser-extension, desktop and mobile client contracts; the exact versions and completed acceptance checks are listed in [client support](docs/client-support.md). Stock Vere 4.6, Gall, Hoon and native Eyre HTTPS serve every production request. Python/Node scripts provide local installation, backup and development/verification tooling; no auth backend, reverse proxy, Bitwarden server library, Vaultwarden code or runtime fork is required.

Connect owns registration, PKCE authorization codes, ship-owner consent and live grant revocation. The Bitwarden desk owns the `cli`/`browser`/`desktop`/`mobile` IDs, `api offline_access` scope, JWT claims, encrypted vault API and bounded refresh retry. See [the generic contract](https://github.com/davetist/urbit-connect/blob/main/docs/resource-integrations.md).

Previous hardening changes and verification: [remaining native hardening](evidence/remaining-native-hardening.md). Exact client/action support and deferred journal checks: [client support](docs/client-support.md). Both public-token derivation issues are fixed for newly issued credentials: public JWT IDs cannot derive refresh credentials, and Connect resource session IDs cannot derive HTTP credentials. Older Connect resource IDs may still reveal their former seed, but Connect rejects credentials derived from them on its HTTP routes. Upgrading the Bitwarden desk from its previous state revokes existing Bitwarden sessions and requires a new SSO sign-in while preserving encrypted vault data. Retention of authorization tokens that cannot decrypt or read passwords is an [accepted known limitation](docs/known-limitations.md), not a usability blocker; the initial CLI compatibility exception is documented alongside the retained session policy.

**Fresh readiness check, 2026-10-16:** the current standalone desks passed the listed CLI, extension, signed macOS and official-source iOS Simulator workflows together. The [CLI sign-in correction](evidence/cli-signin-fix-2026-10-16/assessment.md) passed 16/16 fresh-profile first attempts, actual token-expiry/revocation checks and official CLI vault workflows. The separate Connect consent fix passes at default mobile page scale. See the [actual results and readiness assessment](evidence/current-2026-10-16/assessment.md). This remains a synthetic-data preview.

## Install and connect

Install this desk alongside the latest [Urbit Connect](https://github.com/davetist/urbit-connect) desk on the same ship. Connect is maintained independently; this repository has no pinned Connect version or Git submodule. Its reusable authorization features stay in Connect, while the Bitwarden desk, setup UI, tests, documentation and operator tools live here. The [repository split record](docs/repository-split.md) explains source history and the boundary of the retained evidence.

Use the [installation/update guide](docs/install.md) to select an existing owned ship, verify the source package and import the Connect and Bitwarden desks through stock Clay. HTTPS terminates in native Eyre; the guide covers trusted certificates and native ACME renewal. The installer does not change the ship's DNS, ports or supervisor. Phones need a hostname reachable from the phone and a certificate trusted by the client.

Open `https://your-ship/apps/bitwarden` while logged in as the ship owner. This is also the **self-hosted server URL** to enter in official Bitwarden clients. The desk serves its UI, API and identity endpoints under that prefix, leaving the ship's home page and other applications available. It does not bind `/`, `/api` or `/identity` at the origin root.

The page distinguishes first enrollment from an existing vault, confirms the local vault password, displays the enrolled email and actual connection URLs, and enables the official-client registrations in Connect. During enrollment, browser WebCrypto derives the local password key and encrypts the random user key and RSA private key before sending their envelopes. Existing vaults retain their account keys; enabling a new client does not re-enroll the vault. The explicit legacy-extension migration button replaces the old callback registration and signs out its existing extension connections without deleting the encrypted vault.

In Bitwarden, select **Self-hosted**, enter the displayed server URL and enrolled email, then choose **Single sign-on** or **Enterprise SSO** with organization `urbit-vault`. Approve through Connect on the ship and unlock locally with the enrollment password. The official clients encrypt and decrypt vault items; Connect manages authorization only. The ship page is setup/SSO, not a replacement web vault.

## Personal-vault scope

The desk implements personal item create/edit/read, trash/restore, folders, and encrypted personal-vault import. Import preserves folder relationships and reuses existing destination folders when requested. Deleting a folder preserves its items. The current official CLI 2026.9.1 run completed fresh SSO at the scoped URL and encrypted, synchronized and locally decrypted login, secure-note, card and identity records. Native folder/import checks and the official CLI folder/import round-trip passed. [Current functional evidence](evidence/current-2026-10-16/official-cli-usability.json). See [client support](docs/client-support.md) for the distinction between implemented API behavior, source-confirmed client contracts and completed official-client checks.

Synchronization supports the official `/sync` and account-revision APIs. Clients upload their changes immediately. Automatic initial sync was demonstrated in the extension, signed macOS desktop and official-source iOS Simulator; explicit cross-client **Sync now** also passed. Longer fallback/lifecycle refresh intervals remain source-confirmed rather than timed acceptance results. Immediate server-pushed updates are not implemented: desktop/extension SignalR is WebSocket-only, and mobile push uses APNs/FCM. This does not mean every sync must be manual. The [automatic-sync section](docs/client-support.md#automatic-sync-and-immediate-updates) records the actual client timing and native transport limit.

Personal vault export is performed by the official client, including its password-protected JSON format; no server-side password-verification endpoint is needed for that contract. The current CLI JSON export → delete → import rehearsal recovered all four personal item types and their folder relationships; its temporary plaintext file was removed. Password-protected JSON is source-confirmed but has not completed runtime acceptance. For full account and wrapped-key recovery, use the [stopped-pier backup/restore guide](docs/backup.md). Existing accounts from another backend need export/import into this enrolled account, rather than merely changing their server URL.

Fresh extension SSO, password editing and controlled-page autofill passed. The signed macOS desktop completed SSO/local unlock and note create/edit/readback. An unchanged official iOS release-source build in Simulator completed SSO/local unlock, note creation/title/body edit, cross-client sync and restart/local re-unlock. Android has source-contract support only; physical devices, App Store iOS and other desktop operating systems remain unqualified. Native deployment and full stopped-pier recovery also passed, including official CLI decryption on the restored fake ship, with the original stopped copy preserved. See the [evidence boundary](docs/client-support.md#versions-and-evidence-boundary).

This remains a single-account synthetic-data preview, not a full Bitwarden server or completed production security assessment. Organizations, attachments, Sends, passkeys, immediate push delivery, password changes, account deletion and API keys are outside this version. Automatic 30-day trash purging is not implemented even though stock clients may display that message. The two token-derivation repairs are present in the tested sources; expanded journal and adversarial validation was not rerun.

Ordinary password sign-in remains disabled. The previously exercised CLI prelogin rejection is historical evidence; expanded transmission/journal checks have not been rerun. Unsupported account actions are not covered by the SSO/local-unlock qualification, and a server rejection cannot establish what an arbitrary client sent beforehand.

## Reproduce on Apple Silicon macOS

Prerequisites: Git, Python 3.10+, Node 22.12+, npm, OpenSSL, the repository's pinned stock Vere and pill (`toolchain.json`). `node_modules/playwright` and Chrome for Testing 151.0.7922.34 are needed for the browser harness. Setup pins browser installation through Playwright 1.62.1 (revision 1234), independently of the newer web-test package. Client downloads are pinned in `artifacts.json`; no account or paid service is needed. The dedicated fixture lives exclusively under `.work/bitwarden-sso`, with loopback ports HTTP 19680, native HTTPS 19681 and Ames 19682. Keep this directory private: it contains synthetic credentials, cookies, tokens, keys, client profiles and journal data.

```sh
npm ci
python3 scripts/setup.py
node scripts/browser.mjs --enroll
```

Run these commands from this repository root. Setup obtains the latest Connect source from `main` into ignored `.work/dependencies/urbit-connect`; set `URBIT_CONNECT_ROOT` to an existing Connect checkout when developing both desks locally. This source checkout supports installation and generic regression tests; production requests remain entirely within the installed Urbit desks.

Setup refuses occupied ports for a new fixture and never reuses other piers. The fixture certificate is trusted only by the test CLI via `NODE_EXTRA_CA_CERTS` and by the isolated browser via its exact SPKI pin; no global trust change. If Chrome disables the unpacked official release, enable Developer mode in this isolated profile at `chrome://extensions`. The harness preserves official extension files byte-for-byte. Set `BW_BROWSER_EXECUTABLE` only if the Playwright browser path is unavailable.

The harness prints a private stdio control interface; it opens no debugging TCP port. Start official CLI SSO from a PTY using `python3 scripts/cli_sso.py`, then open the captured URL from private `cli-browser-url.json` in that same owner-authenticated browser. The PATH-only browser-opener shim captures the official URL; it does not alter client code or protocol. Approve the real UI. The CLI uses its own loopback callback listener. Extension settings should use self-hosted `https://localhost:19681/apps/bitwarden`, SSO organization `urbit-vault`, and the same email. Its official connector returns the code/state with the upstream postMessage contract.

After enrollment, scripts `cli_ops.py create`, `read` and `delete` use the official CLI; the password is passed only to local `unlock --passwordenv`, never in argv. `test_generic.py` expects the unrelated `notes-native` registration created by `test_policy.py`. Existing protocol, hardening, pending, restart, resource-revoke and official-negative scripts use the selected fixture. Mixed security suites remain deferred during the current usability work. `test_connect_regressions.py` removes its registrations and revokes all previous test sessions; run it last, after client acceptance. It substitutes fixture paths/control in the selected Connect checkout's HTTP tests without changing their assertions. Those regression helpers are development dependencies, not part of the running Bitwarden backend.

Stop the owned fixture with `python3 scripts/stop.py`. No script deletes the evidence or other fixtures.

## Boundaries and recovery

The initial CLI SSO access token expires after six minutes to avoid the official CLI’s immediate-refresh startup race; subsequent newly minted CLI access tokens and all other clients expire after 60 seconds. An identical response within the five-second retry cache can still contain the initial token. Connect's 30-day absolute grant lifetime remains authoritative and is not extended by refresh. JWT signatures are native Hoon HMAC-SHA256, but API acceptance also requires exact token-digest membership and a live Connect grant. Refreshes rotate once, with a five-second cache returning the same response to overlapping official-client retries. Native Behn timers expire those responses during idle operation; reload prunes expired entries and re-arms valid ones. Historical journal/snapshot copies are not erased. A consumed predecessor used after grace revokes both Bitwarden and Connect sessions. Each Bitwarden session family retains at most 4,096 consumed refresh digests; reaching that limit requires a new SSO authorization. Owner revocation is checked before the retry cache. Logout using a current or consumed refresh token deletes the family and releases its Connect grant. The ordinary Connect document-client refresh policy is unchanged.

Pending code exchanges are limited to 32 and time out after 30 seconds with HTTP 503. Reload completes held HTTP requests with 503. Late successful exchanges are revoked instead of becoming orphan grants. Enrollment can resume after partial registration failure; it reuses only matching enabled policies and refuses to overwrite conflicting clients.

Ordinary requests are limited to 256 KiB; the encrypted bulk-import endpoint accepts up to 6 MiB so official clients can submit a vault in one request. Stored ciphers remain limited to 64 KiB each, 1,000 items including soft deletes, and 4 MiB aggregate cipher data, with reserved deletion metadata. Folders are limited to 1,000 entries, 64 KiB per serialized record and 1 MiB aggregate. Imports validate the complete candidate before committing its items, folders and revision. Hard deletion releases capacity. Stale item revisions return 409. Sync is not paginated.

Revocation prevents further server access; it cannot erase plaintext or encrypted data already cached by a client. Local unlock may remain possible after revocation. The ship retains encrypted vault data, wrapped account keys and metadata. Its event history can also retain owner cookies, authorization codes and access/refresh authorization tokens. **Access/refresh tokens cannot decrypt the vault or read passwords.** A still-valid token can authorize downloading, modifying or deleting encrypted vault data; it is not the master password or unwrapped vault key. This token-retention limitation is accepted and does not change the session policy. The synthetic journal audit checks specific known password/hash/key values across raw LMDB and decoded input events separately from active Gall state. It is evidence for tested flows, not a proof that no conceivable encoding or unsupported action can journal a secret.

## Historical security evidence — deferred during this work

The following is the existing audit procedure, not a check executed or authorized by the current usability work. Run it only when the separate validation restriction is lifted.

Run `python3 scripts/audit.py` after browser enrollment and exercised client workflows, while the fixture is running and its `cli` registration still exists. The runner creates an isolated Python venv, installs pinned **lmdb 1.7.5** (read-only audit tooling, not server code), obtains a fresh probe token, exports both active Gall states through the stock local control socket without rendering their contents, verifies a native JWT against Python HMAC, and scans the raw LMDB plus decoded input events. Its prerequisites are the private files produced by setup and `browser.mjs --enroll`; the browser harness saves request traffic after each UI operation. Evidence is written to `evidence/history-audit.json`. All three positive controls—encrypted key envelope, owner cookie and issued access token—must appear in decoded events. No secret value is written to public evidence.

The separate `test_connect_regressions.py` intentionally removes the Bitwarden client registrations. Run the audit first, or restore the exact registration policies before auditing afterward. Private logs and piers are excluded from source packaging.

The [current usability verification](evidence/current-2026-10-16/assessment.md) records actual clients, automatic-sync boundaries, recovery and cleanup.
