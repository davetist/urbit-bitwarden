# Urbitwarden desk

Urbitwarden is an independent project, not affiliated with or endorsed by Bitwarden. This native Gall desk connects official Bitwarden clients to Connect's reusable local-resource authorization through Enterprise SSO. The backend implements CLI, browser-extension, desktop and mobile client contracts; the exact versions and completed acceptance checks are listed in [client support](docs/client-support.md). Stock Vere 4.6, Gall, Hoon and Eyre serve application requests; clients require trusted HTTPS, which may terminate in Eyre or an existing trusted ingress. Python/Node scripts provide local installation, backup and development/verification tooling; no external auth backend, Bitwarden server library, Vaultwarden code or runtime fork is required.

Report maintenance issues through [GitHub Issues](https://github.com/davetist/urbit-bitwarden/issues) and sensitive vulnerabilities through [private vulnerability reporting](https://github.com/davetist/urbit-bitwarden/security/advisories/new).

[0.2.0 release notes](docs/release-0.2.0.md) summarize supported client flows, upgrade behavior and verification limits.

Connect owns registration, PKCE authorization codes, ship-owner consent and live grant revocation. The Urbitwarden desk maps the official `cli`/`browser`/`desktop`/`mobile` wire IDs to `urbitwarden-cli`/`urbitwarden-browser`/`urbitwarden-desktop`/`urbitwarden-mobile` registrations and owns the `api offline_access` scope, JWT claims, encrypted vault API and bounded refresh retry. See [the generic contract](https://github.com/davetist/urbit-connect/blob/main/docs/resource-integrations.md).

Previous hardening changes and verification: [remaining native hardening](evidence/remaining-native-hardening.md). Exact client/action support and deferred journal checks: [client support](docs/client-support.md). Both public-token derivation issues are fixed for newly issued credentials: public JWT IDs cannot derive refresh credentials, and Connect resource session IDs cannot derive HTTP credentials. Older Connect resource IDs may still reveal their former seed, but Connect rejects credentials derived from them on its HTTP routes. Migration from legacy `%0` state revokes its old Bitwarden sessions while preserving encrypted vault data. The personal-vault `%1` → `%2` migration preserves existing sessions and data while adding attachment storage and optional trash scheduling. Retention of authorization tokens that cannot decrypt or read passwords is an [accepted known limitation](docs/known-limitations.md), not a usability blocker; the initial CLI compatibility exception is documented alongside the retained session policy.

**Historical observations before quota removal, 2026-10-16:** the then-current standalone desks passed the listed CLI, extension, signed macOS and official-source iOS Simulator workflows together. The [CLI sign-in correction](evidence/cli-signin-fix-2026-10-16/assessment.md) passed 16/16 fresh-profile first attempts, actual token-expiry/revocation checks and official CLI vault workflows. The separate Connect consent fix passes at default mobile page scale. See the [actual results and readiness assessment](evidence/current-2026-10-16/assessment.md). These are historical observations, not mandatory qualification gates. See the [current development policy](docs/readiness-policy.md).

## Install and connect

For a quick first run, use the [tester guide](docs/tester-guide.md).

Install this desk alongside the latest [Urbit Connect](https://github.com/davetist/urbit-connect) desk on the same ship. Connect is maintained independently; this repository has no pinned Connect version or Git submodule. Its reusable authorization features stay in Connect, while the Urbitwarden desk, setup UI, tests, documentation and operator tools live here. The [repository split record](docs/repository-split.md) explains source history and the boundary of the retained evidence.

Use the [installation/update guide](docs/install.md) to select an existing owned ship, verify the source package and import the Connect and Urbitwarden desks through stock Clay. HTTPS terminates in native Eyre; the guide covers trusted certificates and native ACME renewal. The installer does not change the ship's DNS, ports or supervisor. Phones need a hostname reachable from the phone and a certificate trusted by the client.

After installation, Landscape shows a **Urbitwarden** tile using the bundled shield image. Clicking it opens `/apps/urbitwarden`. The desk includes its Docket metadata, mark and parser dependencies; no separate glob upload or image host is required.

Open `https://your-ship/apps/urbitwarden` while logged in as the ship owner. Logged-out visitors are sent immediately to the ship login without receiving the Urbitwarden page or its JavaScript/CSS. A minimal redirect-only document preserves URL fragments used by official-client SSO; after login, the browser returns to the requested page. Protocol endpoints required by official clients remain available under their existing authorization rules. This is also the **self-hosted server URL** to enter in official Bitwarden clients. The desk serves its UI, API and identity endpoints under that prefix, leaving the ship's home page and other applications available. It does not bind `/`, `/api` or `/identity` at the origin root.

The page distinguishes first enrollment from an existing vault, confirms the local vault password, and displays the enrolled email and connection URLs. Enrollment configures Connect without creating app registrations. A valid SSO attempt registers only that client, through the ship owner's authenticated browser, before Connect asks for approval. Each client has a namespaced ID such as `urbitwarden-desktop`; unused clients do not appear. Disabled registrations stay disabled. Matching legacy registrations can be renamed without losing sessions or changing the encrypted vault; conflicting policies require owner review.

During enrollment, browser WebCrypto derives the local password key and encrypts the random user key and RSA private key before sending their envelopes. Existing vaults retain their account keys; connecting another client does not re-enroll the vault.

In Bitwarden, select **Self-hosted**, enter the displayed server URL and enrolled email, then choose **Single sign-on** or **Enterprise SSO** with organization `urbit-vault`. Approve through Connect on the ship and unlock locally with the enrollment password. The official clients encrypt and decrypt vault items; Connect manages authorization only. The ship page is setup/SSO, not a replacement web vault.

## Personal-vault scope

The desk implements personal item create/edit/read, trash/restore, folders, and encrypted personal-vault import. Import preserves folder relationships and reuses existing destination folders when requested. Deleting a folder preserves its items. The historical official CLI 2026.9.1 run completed fresh SSO at the scoped URL and encrypted, synchronized and locally decrypted login, secure-note, card and identity records. Native folder/import checks and the official CLI folder/import round-trip passed. [Historical functional evidence](evidence/current-2026-10-16/official-cli-usability.json). See [client support](docs/client-support.md) for the distinction between implemented API behavior, source-confirmed client contracts and completed official-client checks.

Synchronization supports the official `/sync` and account-revision APIs. Clients upload their changes immediately. Automatic initial sync was demonstrated in the extension, signed macOS desktop and official-source iOS Simulator; explicit cross-client **Sync now** also passed. Longer fallback/lifecycle refresh intervals remain source-confirmed rather than timed acceptance results. Immediate server-pushed updates are not implemented: desktop/extension SignalR is WebSocket-only, and mobile push uses APNs/FCM. This does not mean every sync must be manual. The [automatic-sync section](docs/client-support.md#automatic-sync-and-immediate-updates) records the actual client timing and native transport limit.

Personal vault export is performed by the official client, including its password-protected JSON format; no server-side password-verification endpoint is needed for that contract. The current official CLI 2026.10.0 exported and reimported selected items, and separately uploaded, downloaded and decrypted an encrypted attachment. Password-protected JSON is source-confirmed but has not completed runtime acceptance. For wrapped-key and encrypted-content recovery onto a different ship, use the [portable vault backup guide](docs/backup.md). Existing accounts from another backend need export/import into this enrolled account, rather than merely changing their server URL.

Fresh extension SSO, password editing and controlled-page autofill passed. The signed macOS desktop completed SSO/local unlock, note create/edit/readback and native master-password change with new-password unlock and sync. An unchanged official iOS release-source build in Simulator completed SSO/local unlock, note creation/title/body edit, cross-client sync and restart/local re-unlock. Android has source-contract support only; physical devices, App Store iOS and other desktop operating systems have not been exercised here. Disposable-ship tests demonstrated in-place alpha-to-candidate data preservation with fresh SSO after account-ID migration, plus encrypted portable vault recovery and official CLI decryption on a different ship. See [client support](docs/client-support.md#release-candidate-checks--2026-10-24) for the exact evidence boundary.

The product is a personal vault with Connect-only authentication. The [Vaultwarden parity scope](docs/vaultwarden-parity.md) records implemented server contracts and official-client UI boundaries. Shared vaults, organizations, Sends and a browser web vault are deferred by the owner; API-key and password sign-in remain intentionally excluded. Attachment and import/export workflows passed in the current official CLI; website passkey creation/use passed in the current official extension on an owned test ship. A synthetic API-initiated PBKDF2 change passed fresh official CLI sign-in, unlock and decryption. **Changing KDF settings is outside the 0.2.0 stable user-facing support scope:** the official control requires a Bitwarden web vault, which this release does not provide. Connect-authorized password/KDF/key changes, vault purge and account deletion are implemented in source with the approved request-history disclosure; the KDF API compatibility check does not establish an end-user settings workflow. Trash expiry is optional and disabled by default, even when a stock client displays a 30-day message. The two token-derivation repairs are present in the tested sources; expanded journal and adversarial validation was not rerun.

Ordinary password sign-in remains disabled. The previously exercised CLI prelogin rejection is historical evidence; expanded transmission/journal checks have not been rerun. Unsupported account actions are not covered by the SSO/local-unlock qualification, and a server rejection cannot establish what an arbitrary client sent beforehand.

## Boundaries and recovery

The initial CLI SSO access token expires after six minutes to avoid the official CLI’s immediate-refresh startup race; subsequent newly minted CLI access tokens and all other clients expire after 60 seconds. An identical response within the five-second retry cache can still contain the initial token. Connect's 30-day absolute grant lifetime remains authoritative and is not extended by refresh. JWT signatures are native Hoon HMAC-SHA256, but API acceptance also requires exact token-digest membership and a live Connect grant. Refreshes rotate once, with a five-second cache returning the same response to overlapping official-client retries. Native Behn timers expire those responses during idle operation; reload prunes expired entries and re-arms valid ones. Historical journal/snapshot copies are not erased. A consumed predecessor used after grace revokes both Bitwarden and Connect sessions. Each Bitwarden session family retains at most 4,096 consumed refresh digests; reaching that limit requires a new SSO authorization. Owner revocation is checked before the retry cache. Logout using a current or consumed refresh token deletes the family and releases its Connect grant. The ordinary Connect document-client refresh policy is unchanged.

Pending code exchanges are limited to 32 and time out after 30 seconds with HTTP 503. Reload completes held HTTP requests with 503. Late successful exchanges are revoked instead of becoming orphan grants. Enrollment can resume after partial registration failure; it reuses only matching enabled policies and refuses to overwrite conflicting clients.

The desk does not impose a separate request/import byte ceiling. There are no desk-imposed retained-item or folder count quotas, per-record storage quotas, or total vault/folder byte quotas. Host/runtime resources still determine practical capacity. Imports validate the complete candidate before committing its items, folders and revision. Hard deletion releases capacity. Stale item revisions return 409. Sync is not paginated.

Revocation prevents further server access; it cannot erase plaintext or encrypted data already cached by a client. Local unlock may remain possible after revocation. The ship retains encrypted vault data, wrapped account keys and metadata. Its event history can also retain owner cookies, authorization codes and access/refresh authorization tokens. **Access/refresh tokens cannot decrypt the vault or read passwords.** A still-valid token can authorize downloading, modifying or deleting encrypted vault data; it is not the master password or unwrapped vault key. This token-retention limitation is accepted and does not change the session policy. The historical synthetic journal audit checked specific known password/hash/key values across raw LMDB and decoded input events separately from active Gall state. It is evidence for those earlier flows, not a guarantee for new account-management operations. Official-client password/KDF/key changes and some purge/delete requests can leave password-derived verification hashes in history; the desk does not retain or verify them in active account state. See the [approved management boundary](docs/known-limitations.md#account-management-request-history).
