# Sign-in and consent follow-up — 2026-10-16

The iOS consent layout is fixed in the separate Connect desk. The unchanged official iOS 2026.9.1 (3533) source build completed actual SSO approval at default page scale, normal callback, local unlock and initial sync on a fresh iOS 26.5 iPhone 17 Pro Simulator. Both decisions stayed above the system-browser toolbar, and native touch scrolling revealed the complete retained permission explanation. [Native result](ios-results.json) and [Connect implementation/evidence](https://github.com/davetist/urbit-connect/blob/main/docs/consent-layout.md).

The official CLI first-attempt issue is reproduced but **not fixed yet**. Eight new profiles each made one browser-approved sign-in attempt with the unmodified CLI 2026.9.1: seven passed and attempt five exited with the same `Refresh Access token error` as the earlier run. [Attempt results](baseline-results.json), [sanitized diagnosis](cli-diagnosis.json). The official archive/extracted-client and stock-runtime hashes were verified again. No prior authenticated profile counted as fresh acceptance.

The pinned CLI stores the access token before the refresh token in [`setTokens`](https://github.com/bitwarden/clients/blob/cli-v2026.9.1/libs/common/src/auth/services/token.service.ts#L199-L214). It considers a token with less than five minutes remaining to need refresh in [`tokenNeedsRefresh`](https://github.com/bitwarden/clients/blob/cli-v2026.9.1/libs/common/src/auth/services/token.service.ts#L1029-L1032). The observed exception is raised when neither a refresh token nor API credentials are locally available in [`internalRefreshToken`](https://github.com/bitwarden/clients/blob/cli-v2026.9.1/libs/common/src/services/api.service.ts#L1521-L1535). A fresh 60-second desk token is already inside that refresh window. This supports a startup persistence race, but the exact concurrent caller has not been proven from the captured stack. The explicit login sync occurs later and skips token refresh.

The newer official CLI `2026.10.0`, released 2026-10-15, was checked as a possible policy-preserving alternative. Its token service and login command sources are unchanged from `2026.9.1`; its API service retains the same refresh path. No runtime acceptance or fix is claimed for that newer version.

The proposed narrow compatibility change is a six-minute **initial CLI** access token, followed by 60-second newly minted tokens. Other clients, the 30-day absolute grant and five-second identical-response cache remain unchanged. An immediate refresh inside that five-second cache may return the original initial token; it is not a newly minted token. JWT expiration, stored server expiry and `expires_in` must agree. Owner revocation remains authoritative.

This proposal awaits the owner's decision because [known limitations](../../docs/known-limitations.md) records an explicit instruction to keep token lifetimes unchanged. No authentication source or lifetime policy was changed in this follow-up. A private issuance-contract probe fails on the existing 60-second token as expected, but no mitigation or post-fix CLI success is claimed. The fresh-profile profiles, diagnostic source copies and raw results remain private outside Git.

The broader single-account synthetic-data preview and production/independent qualification limits remain unchanged. The earlier [acceptance record](../current-2026-10-16/assessment.md) is retained as historical evidence; its mobile page-scale workaround is superseded by the native consent result above.
